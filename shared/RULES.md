# 通用小说规则 V1

> 来源：当前累计的高可信原生元数据、24本 deep、8本 extreme、强弱对照、统一编码、Click/Retention 分层、平台审计与正文试写反证。
> 用途：作为所有后续小说项目的默认检查表，不是不可违反的教条。

## 0. 正文语言层必须经过独立闸门

本文件主要约束故事结构、爽点、因果和留存，不能替代正文语言审计。

所有小说正文、试写章节和大幅改稿必须同时遵守：

> `shared/PROSE_RULES.md`
>
> `shared/META_NARRATIVE_RULES.md`

强制流程是：读取当前小说自己的风格/连续性规则与本文件 → 读取 `shared/PROSE_RULES.md` 与 `shared/META_NARRATIVE_RULES.md` → 写第一稿 → 运行 prose scan 与 meta-narrative scan → 人工复核全部高风险命中 → 再交付或提交正文。

至少运行：

```bash
python shared/tools/prose_guard.py <chapter.md>
python shared/tools/meta_narrative_guard.py <chapter.md>
```

元叙事扫描的 `HARD` 必须为 0；`WARN` 必须逐条人工确认。不能只因为章节卡和爽点结构通过，就跳过语言层检查；也不能为了“去 AI 味”机械碎句、批量换同义词或清除正常文学表达。

## 1. Click：先让第一因果容易复述

不是“概念越少越好”，而是读者能否很快说清：

> 谁遇到什么具体问题 → 有什么异常资源/能力 → 第一笔现实利益或损失是什么。

专业题材可以复杂，但专业背景不应成为理解第一利益的前提。

## 2. Activation：首屏先给幻想，前三章尽快兑现

- 前几百字优先建立“为什么这能力值得看”，不要先要求读者学习题材知识；
- 核心能力尽快改变一个任何普通读者都能理解的结果；
- 技术发现、线索、准确率、流程优化本身通常不算爽点，必须继续兑换成读者能立刻感知的收益；
- 主角本人仍应负责选择目标、决定资源怎么花、决定能力用于哪里并承担后果；
- 不机械要求前三章发财，但不能只解释设定。

## 3. 爽点必须完成“优势 → 对比 → 收益”

写完一个准备当爽点的节点，强制回答：

> 普通人/对手正常只能怎样？
>
> 主角凭核心能力明显强在哪里、强多少？
>
> 这次优势立刻换来了什么？

可兑换收益包括但不限于：钱、订单、资格、装备、资源、权限、地位、生存能力、身体提升、公开结果。

如果只能回答“发现了一个新线索”“准确率更高了”“流程更先进了”，通常仍只是过程，不是结算。

## 4. 让读者能自己脑补后续上限

强开局不只解决眼前问题，还要让读者自然产生：

> “如果这个能力继续用在更大的对象上，会变成什么？”

第一章应尽量出现一个可扩张的幻想结构，而不是只能服务当前事故的一次性技巧。

## 5. 读者看得到的资源尽量榨干价值

如果正文明确摆出一批废品、奖励、机会、敌人资产或失败样本，后续应说明它们的主要去向。

避免只取其中一件完成剧情、其余大量资源像不存在一样。

可以拆成：直接收益、修复复用、材料回收、经验积累、下一阶段储备、融合升级等。

目标不是记流水账，而是让读者感到主角“会过日子、会吃干抹净、不会浪费外挂价值”。

## 6. Retention：爽点必须组成进展，而不是功能巡演

连续事件应围绕同一个阶段目标不断拆解、累计、结算，并在结算后留下下一格空间。

重点检查：

- `progress_architecture`：是否聚焦、累计、可阶段结算；
- `causal_ownership`：成果是否真正属于主角的选择与行动；
- `friction_survival`：外挂解决一组问题后，是否还有更大对象、更高代差、更强敌人或更高层级目标继续承接。

避免：这一章黑客、下一章投资、再下一章格斗，只是在展示“我还能做什么”。

## 7. 强外挂可以直接跨越正常成本

爽文外挂没有义务把现实研发、制造、验证、融资流程重新完整走一遍。

只要大逻辑稳定，能力可以直接：

- 给技术；
- 修复/重构物品；
- 压缩制造时间；
- 把资源转化为成品；
- 强化主角或装备。

小逻辑服务爽感，不为“现实严谨”牺牲核心幻想。需要限制时，限制应创造下一层爽点，而不是把外挂重新削成普通工具。

## 8. 主角不能被能力吃空

即使能力能直接产出结果，主角仍至少持续负责其中多数高价值选择：

- 吃哪一种失败/资源；
- 选择哪条升级方向；
- 给谁用、什么时候用；
- 保留还是出售；
- 如何利用成果形成下一次资源优势；
- 关键冲突中承担结果。

“系统替他造”不等于“主角没有作用”；主角的核心价值可以从劳动执行转移到资源配置和路线选择。

## 9. 多题材可以共存，但成长主轴必须统一

商业、科技、装备、战斗、个人进化可以同时存在，但最好共享同一种核心资源和成长逻辑。

例如：商业负责获得失败项目，失败项目供给技术，技术生成装备，装备暴露人体短板，人体失败又推动个人进化。

这样不是模块巡演，而是一条不断升级的因果链。

## 10. 第一计分板要有成长余量

第一阶段应尽快结算，但不能把整本书的天花板提前打满。

更稳的结构是：

> 第一笔直观收益 → 可复制优势 → 更大对象 → 主角自身受益 → 更高层级资源/敌人 → 再升级。

钱可以是早期计分板，但不应默认成为所有题材的最终计分板。

## 11. 平台数据必须分层解释

任何“在读低/收藏低/订阅低”都不能自动证明作品结构失败。

至少区分：

- 平台原生还是分发；
- 是否进入推荐/验证期；
- 曝光是否可观测；
- 作品年龄与观察窗口；
- 更新/停更/完结状态；
- 各平台指标语义。

Click、Activation、Retention、Scale 不允许混成一个原因。

## 12. 对反馈学习型机制的额外要求

如果作品明确卖“从真实反馈成长”，循环应读者可见，但不要把验证流程本身写成主要消费内容。

更适合爽文的表达是：

> 失败发生 → 能力立刻吃掉失败价值 → 直接形成可用优势 → 在现实中兑现 → 更大的失败/资源出现。

底层验证可以作为作者规则存在，但前台优先展示收益。

## 13. 写作时优先事件，少用作者替读者下结论

“震惊、无敌、降维打击”可以用，但前面最好已经有具体事件、数字、对象或行为作为骨架。

优先让读者从事件判断结果，而不是连续由旁白宣布结果很厉害。

## 14. 研究停止规则

以后立项研究不再以“样本越多越好”为目标。

当满足以下条件时，应停止泛化深读，转入设计/发布测试：

- 关键结论删掉单个强样本后不翻转；
- 每个一级判断至少有多个独立正例，并有反例/控制；
- 最近一批定向样本不再产生新的一级变量；
- 剩余最大未知只能通过真实曝光、点击、留存或更新数据获得。

正文试写如果暴露“读者看不到收益”等问题，优先回到已知样本检查兑现方式，而不是重新无限扩样本。

## 15. shared 与单本小说的边界

这份规则默认适用于所有项目，但不是强制模板。

如果某一本小说的题材需要例外：

- 在该小说自己的目录记录原因；
- 不要为了迁就一部作品随意修改 shared 规则；
- 只有当新证据与既有强样本共同支持时，再升级 shared。

## 16. 人物连续性要同时通过“事实”与“读者记忆”两层

角色在设定表、连续性账本里存在，不代表读者还记得他。

长篇续写重新调用旧人物时，除了确认姓名、关系、岗位和经历没有冲突，还必须检查**读者上一次真正看见他做事是什么时候**。

以下情况优先在重登场的第一处加入一句自然身份锚点：

- 长时间没有有效出场；
- 首次出场发生在多人同时加入、群体救援、高压高潮或大量系统信息中；
- 角色曾只是路人/临时成员，后来被重新调用承担重要剧情；
- 同一篇章存在姓名相近、职业相近或功能相近的人物；
- 跨卷、跨地图或跨很长篇幅重新出现。

身份锚点应依附于当前动作，例如“当初留在某站的某人又发来消息”“负责外勤的某人把车停好”，而不是插入人物简历或章节回顾。

高频角色也不要反复介绍。目标是让读者在需要时**一秒恢复人物关系**，不是每次出场都重新教学。

**重写人物入场时还要检查时间顺序。** 如果人物的首次相识、加入或转正章节被后移、拆分或重写，必须反向搜索此前正文中的姓名、岗位和动作残留。人物在剧情上尚未出现，却已经被更早章节当成熟人使用，属于事实连续性错误，不是“读者忘了”；应先修掉提前泄漏，不能靠后文再介绍一次掩盖。

长篇项目建议单独维护人物读者记忆账本，至少记录：首次出场、首次记忆点、身份变化、最近有效出场、长空窗重登场要求。发布前应检查是否存在“作者知道是谁，所以直接裸名字写回正文”的情况。
